## 1. ระบบนี้คืออะไร

**ร้านขาย–ติดตั้ง–ซ่อมเครื่องใช้ไฟฟ้า/แอร์ในไทย ใช้ CRM ทั้งระบบผ่าน LINE**

พนักงานขายพิมพ์ `เปิดดีลให้สมชาย` ในไลน์แล้วดีลถูกสร้าง · ช่างพิมพ์ `เช็คอิน` เมื่อถึงหน้างาน · ลูกค้าพิมพ์ `แอร์ไม่เย็น` แล้วใบงานซ่อมถูกเปิดให้ ไม่มีการฝึกใช้โปรแกรม ไม่มีการติดตั้งแอป — ทุกคนใช้ไลน์ที่มีอยู่แล้ว

มี **หน้าจอเว็บ (LIFF) เปิดในไลน์** ด้วย และกฎเหล็กของโปรเจกต์คือ **parity**: อะไรที่ทำได้ในแชทต้องทำได้บนหน้าจอ และกลับกัน (มีสคริปต์ `scripts/dev/check-parity.py` คอยตรวจ)

### LINE Official Account 3 บัญชี

ข้อความมาถึง OA ไหน **เป็นตัวตัดสินทุกอย่าง** — สิทธิ์ ภาษาที่ใช้ตอบ เมนู และแม้แต่ว่าคนคนนี้ "ลงทะเบียนแล้วหรือยัง"

| OA | สี | ใครใช้ | ทำอะไร |
|---|---|---|---|
| `sales` | เขียว `#178a50` | เจ้าของร้าน, แอดมินร้าน, พนักงานขาย (member), CS | ลูกค้า/ดีล/ใบเสนอราคา/สินค้า/ประกัน · มอบหมายงานซ่อม · ตรวจและอนุมัติรายงานช่าง · แชทกับลูกค้า · รายงาน AI + กราฟ · ตั้งค่าร้าน ทีม บทบาท สมาชิก |
| `technician` | น้ำเงิน `#1f6fd6` | ช่างภาคสนาม | รับ/ปฏิเสธงาน · เช็คอิน · ส่งรูปหน้างาน · บอกสถานการณ์ · ปิดงาน + รายงาน 3 ข้อ → PDF |
| `customer` | ส้ม `#e8731a` | ลูกค้าของร้าน | ผูกร้าน · แจ้งซ่อม · ดูสถานะ/เลื่อน/ยกเลิก · ลงทะเบียนสินค้าและประกัน · คุยกับร้าน · ดูสินค้า · ให้คะแนนหลังซ่อม · PDPA |

นอกจากนั้นมี **คอนโซลผู้ดูแลแพลตฟอร์ม** ที่ `/admin` (เว็บ ไม่ผ่านไลน์) สำหรับผู้ดูแลระบบ ไม่ใช่ของร้าน

### วงจรหลักที่ทุกอย่างวิ่งผ่าน

```
ร้านบันทึกเครื่องที่ขาย (S/N)
  → ลูกค้าลงทะเบียน S/N ผูกกับร้าน
    → ลูกค้าแจ้งซ่อม           → ได้ใบงาน T-YYYY-NNNN
      → CS มอบหมายช่าง/ทีม
        → ช่างรับงาน
          → ช่างเช็คอินหน้างาน  → ลูกค้าได้แจ้ง "ช่างถึงแล้ว"
            → ช่างปิดงาน + รายงาน 3 ข้อ → SR-YYYY-NNNN
              → CS อนุมัติ / ตีกลับ
                → PDF ออกอัตโนมัติ + ลูกค้าได้ปุ่มให้คะแนน 1–3
```

อีกวงจรหนึ่งคือฝั่งขาย: `ลูกค้า (Lead) → ดีล → รายการสินค้าในดีล → ใบเสนอราคา → ออกเอกสาร PDF`

### ใครเป็นใคร

| ผู้ใช้ | เข้าทาง | หมายเหตุ |
|---|---|---|
| เจ้าของร้าน (`owner`) | Sales OA | คนแรกที่สร้างร้าน · 1 คนต่อร้าน · โอนได้แบบสองฝ่ายยืนยัน |
| แอดมินร้าน (`admin`) | Sales OA | ทุกสิทธิ์ยกเว้นสิทธิ์แพลตฟอร์ม |
| พนักงานขาย (`member`) | Sales OA | ลูกค้า/ดีล/ใบเสนอราคา/ประกัน/แชทลูกค้า/รายงาน |
| ฝ่ายบริการลูกค้า (`cs`) | Sales OA | ใบงาน มอบหมาย อนุมัติ แชทลูกค้า |
| ช่าง (`technician`) | Technician OA | ใบงานและรายงานบริการเท่านั้น |
| ลูกค้าของร้าน | Customer OA | ไม่ถือ permission key ใด ๆ ในแชท (ดูข้อ 3 และ 8) |
| ผู้ดูแลแพลตฟอร์ม | เว็บ `/admin` | ข้ามร้านได้ ทุกการกระทำถูก audit |

## 2. สถาปัตยกรรม

### สี่ชั้น คุยลงล่างทางเดียว

| ชั้น | ไดเรกทอรี | เป็นเจ้าของอะไร | คุยกับใคร | พอร์ต dev |
|---|---|---|---|---|
| Presentation | `presentation/` (Next.js App Router) | หน้า LIFF, คอนโซล `/admin`, proxy route ฝั่งเซิร์ฟเวอร์ใต้ `app/api/…` | Application เท่านั้น | 3000 |
| Application | `application/chann_app/` (FastAPI) | LINE webhook, การตีความประโยค (intent), กติกาธุรกิจทั้งหมด, API ให้ LIFF/admin | Data ผ่าน `DataClient` | 8080 |
| Data | `data/chann_data/` (FastAPI + SQLAlchemy) | **ชั้นเดียวที่แตะ PostgreSQL/Redis ได้** | Postgres + Redis | 8081 |
| Database | `database/` (Alembic + `seed_reference.py`) | schema, migration, ข้อมูลอ้างอิงตั้งต้น | — | PG 5432 · Redis 6379 |

กฎนี้ **บังคับด้วยเทสต์จริง** ที่ `tests/boundary/test_tier_boundaries.py` — Application ห้าม import SQLAlchemy/psycopg/redis, Presentation ห้ามเรียก Data ตรง

> **สิ่งที่คนทดสอบต้องรู้จากข้อนี้:** เวลาอะไรพัง ให้ถามก่อนว่าพังชั้นไหน
> - หน้าจอขึ้น `503 · application tier unreachable` = Presentation ต่อ Application ไม่ได้
> - คำตอบในแชทเป็น "ขออภัย …" แบบกลาง ๆ = handler ระเบิดแล้วถูกจับไว้ (`unavailable_reply`) ไม่ใช่ระบบเงียบ
> - `/health` ของ Data บอก `schema_state: stale` = image ของ data ใหม่กว่าฐานข้อมูล (ยังไม่ได้รัน migration)

### การพิสูจน์ตัวตนระหว่างชั้น

| จาก → ถึง | วิธี |
|---|---|
| Application → Data | header `X-Internal-Secret` เทียบ `ADMIN_SECRET` · ถ้า secret ว่าง = ตอบ 503 `REQUIRED_NOT_CONFIGURED` ไม่เคยเปิดโล่ง |
| Presentation → Application | ส่งต่อ `X-Liff-ID-Token`, `X-Liff-Audience`, `X-License-Id` เท่านั้น |
| Scheduler → Application | header `X-Sweep-Secret` |
| LIFF token | `auth/liff.py::verify_id_token` ยิงไป `https://api.line.me/oauth2/v2.1/verify` |
| Platform admin | JWT + session ใน Redis |
| LINE → Application | `POST /webhook/line/{oa}` ตรวจ HMAC-SHA256 ต่อ OA · oa ไม่รู้จัก → 404 · ไม่มี secret → 503 · ลายเซ็นผิด → 401 |

### สมองของแชทอยู่ที่ไหน

`application/chann_app/services/chat.py` (~16,900 บรรทัด) ข้อความหนึ่งข้อความเดินทางแบบนี้:

1. `POST /webhook/line/{oa}` → ตรวจลายเซ็น → กันข้อความซ้ำด้วย `webhookEventId`
2. หา identity → หา membership ของ **OA นั้น** → รู้ว่าอยู่ร้านไหน (ถ้าอยู่ร้านเดียว)
3. เลือกภาษาจากค่าที่ผู้ใช้ตั้งไว้
4. แยกประเภท: follow / รูป / ตำแหน่ง / ตอบกลับข้อความ / ข้อความธรรมดา
5. **ชั้นกติกา (deterministic)** — trigger phrase, รหัสงาน/ดีล/ลูกค้า, บริบทที่เพิ่งคุย, flow ที่ค้างอยู่ ตอบเองโดยไม่เรียกโมเดล
6. **ชั้นโมเดล** — เฉพาะประโยคอิสระที่กติกาไม่ครอบคลุม โมเดลตอบเป็น JSON `{"action","entity","fields":{},"missing":[]}` แล้วโค้ดชุดเดิมเป็นคนไปทำงาน

**ผลของการแยกสองชั้นนี้:** ถ้าโมเดลล่ม คำสั่งหลักทั้งหมดยังทำงาน — จะได้ `ระบบไม่พร้อมใช้งาน` เฉพาะประโยคที่ต้องพึ่งโมเดลจริง ๆ

ทุกอย่างในขั้นที่ 4–6 ถูกครอบด้วย try/except ที่ตอบข้อความขอโทษกลับไป **ไม่มีกรณีที่ระบบเงียบ** (ยกเว้นที่ตั้งใจให้เงียบ เช่น เหตุการณ์ที่ไม่ใช่ข้อความ)

### Health endpoint

| endpoint | ตอบอะไร |
|---|---|
| Data `GET /health` | `status(ok\|degraded)`, `tier`, `app_env`, `platform_version`, `git_commit`, `database(up\|down)`, `cache(up\|down)`, `schema_state`, `migration_head`, `expected_migration_head` — Redis ล่มไม่ทำให้ unhealthy (ADR-006) |
| Data `GET /ready` | 200/503 · ต้องมีทั้ง database และ cache |
| Application `GET /health` | `status`, `tier`, `app_env`, `platform_version`, `git_commit`, `required_not_configured` (รายชื่อ config ที่ยังไม่ได้ตั้ง) |
| Application `GET /ready` | 200/503 |
| Presentation `GET /api/ready` | 200/503 |

**Boot guard:** `data/chann_data/main.py` ตรึง `EXPECTED_MIGRATION_HEAD = "0026_member_channel"` ถ้าฐานข้อมูลไม่ตรง ระบบ log error และ `/health.status` เป็น `degraded` — ต้องรัน migration ก่อน deploy ชั้น data เสมอ

## 3. ตัวตนและการลงทะเบียน

> **ข้อนี้คือกฎที่ AI เข้าใจผิดบ่อยที่สุด อ่านให้จบก่อนเขียนเคสทดสอบ**

### หนึ่งบัญชีไลน์ = หนึ่ง "คน" แต่ = สามการลงทะเบียน

| ตาราง | ระดับ | เก็บอะไร |
|---|---|---|
| `chann_identities` | **ข้ามร้าน ข้าม OA** | บัญชีไลน์หนึ่งบัญชี = หนึ่งแถว · ชื่อ นามสกุล เบอร์ อีเมล ที่อยู่ ลายเซ็น ความยินยอม PDPA ภาษา/รูปแบบวันที่ |
| `license_members` | **ต่อ (คน, ร้าน, OA)** | บทบาท สถานะ วันเข้าร่วม · คอลัมน์ `channel` เป็น `sales` หรือ `technician` เท่านั้น · unique `(license_id, chann_uid, channel)` |
| `customer_license_links` | **ต่อ (ลูกค้า, ร้าน)** | ลูกค้าผูกกับร้าน · unique `(chann_uid, license_id)` |

**สิ่งที่แชร์ข้าม OA:** ข้อมูลส่วนตัว (ชื่อ เบอร์ อีเมล ที่อยู่), ลายเซ็น, ภาษา/รูปแบบวันที่/เขตเวลา, ความยินยอม PDPA

**สิ่งที่ไม่แชร์:** การเป็นสมาชิกร้าน, บทบาท, สิทธิ์, สถานะ "ลงทะเบียนแล้ว", flow ที่ค้างอยู่ในแชท (เก็บแยกตาม `(chann_uid, oa)`)

### ตัวอย่างที่ต้องได้ถูก

- เจ้าของร้านบน Sales OA เพิ่มเพื่อน **Technician OA** แล้วพิมพ์อะไรก็ได้ → ต้องได้ข้อความทำนอง *"พบข้อมูลส่วนตัวของคุณแล้ว แต่ยังไม่ได้ลงทะเบียนใน LINE นี้"* พร้อมวิธีลงทะเบียนช่าง
  **ต้องไม่ใช่** "เชื่อมต่อบริษัทแล้ว" หรือเข้าใช้งานช่างได้ทันที
- คนคนเดียวกันเป็นทั้งเซลส์และช่างของร้านเดียวกันได้ → มี `license_members` **2 แถว** ต่างกันที่ `channel` แก้บทบาท/ถอดออกได้แยกกัน
- ลูกค้าที่ผูกร้านแล้ว **ไม่มี** แถว `license_members` เลย โดยตั้งใจ — การผูกร้านต้องไม่ทำให้ได้สิทธิ์ของร้าน

### รหัสเชิญ (invite code)

- ขอจาก Sales OA: `ขอรหัสเชิญช่าง` (บทบาท technician) หรือ `ขอรหัสเชิญ` (บทบาท member/cs)
- รหัสมีอายุและจำนวนครั้งที่ใช้ได้ (`max_uses` ค่าเริ่มต้น 1) ใช้เกินถูกปฏิเสธ
- **ช่องทางที่ใช้ได้มาจากบทบาทของรหัส** — `channel_for_role(role)` คืน `technician` ก็ต่อเมื่อชื่อบทบาทเท่ากับ `technician` แบบตรงตัว ที่เหลือทั้งหมด (owner, admin, cs, member และบทบาทที่ร้านสร้างเอง) เป็น `sales`

| รหัสของบทบาท | ใช้ได้บน OA | ใช้ผิด OA แล้วเกิดอะไร |
|---|---|---|
| `technician` | Technician OA เท่านั้น | Data ตอบ 409 · แชทบอกให้ไปใช้บน LINE ที่ถูก |
| `member`, `cs`, บทบาทที่ร้านสร้างเอง | Sales OA เท่านั้น | เช่นเดียวกัน |

> **ช่องโหว่ที่รู้อยู่ (ไม่ใช่บัคใหม่):** `channel` ดูจาก **ชื่อบทบาท** อย่างเดียว ร้านที่สร้างบทบาทช่างโดยตั้งชื่ออื่น (เช่น "ช่างแอร์") จะได้ช่องทาง `sales` — เรื่องนี้อยู่ในรายการที่ต้องแก้ต่อไป ไม่ต้องรายงานซ้ำ

### ลูกค้าผูกร้านอย่างไร

1. เพิ่มเพื่อน Customer OA → พิมพ์อะไรก็ได้
2. ระบบขอความยินยอม PDPA ก่อน — ไม่ยอมรับ = ไม่ผูก ไม่เก็บข้อมูล
3. พิมพ์ **S/N ของเครื่อง** หรือ **รหัสร้าน 8 ตัว** (ร้านดูรหัสตัวเองด้วย `ข้อมูลร้าน`) หรือชื่อร้าน
4. ผูกซ้ำร้านเดิม → บอกว่า "ผูกไว้แล้ว" · อยู่หลายร้าน → มีปุ่มเลือกและคำสั่ง `เปลี่ยนร้าน`
5. ถ้าเบอร์ตรงกับ Lead ที่พนักงานเคยคีย์ไว้ → ผูกเข้ารายการเดิม ไม่สร้างลูกค้าซ้ำ

### รหัสที่พิมพ์ด้วยมือ

`license_code`, `company_code` (8 ตัว) และ `invite_code` (16 ตัว) ใช้ตัวอักษรชุด `ABCDEFGHJKMNPQRSTUVWXYZ23456789` — ไม่มี `0/O/1/I/L` เพราะคนต้องอ่านจากจอแล้วพิมพ์ตาม

## 4. บทบาทและสิทธิ์

**ระบบตัดสินทุกอย่างจาก permission key ไม่ใช่ชื่อบทบาท** ชื่อบทบาทเป็นป้ายที่ร้านตั้งเองได้ และห้ามกลายเป็นนโยบายในโค้ด บทบาทเริ่มต้น 5 แบบเป็นเพียง "ชุดสิทธิ์ตั้งต้น" ที่เจ้าของแก้ได้ในหน้า **บทบาทและทีม**

**แคตตาล็อกมี 48 key** (`data/chann_data/permissions.py::PERMISSION_KEYS`) — นับได้จริงจากโค้ด

### บทบาทเริ่มต้น 5 แบบ

| บทบาท | จำนวน key | ใครควรได้ | ทำอะไรได้โดยสรุป |
|---|---|---|---|
| `owner` | ทั้งหมด (48) | คนสร้างร้าน 1 คน | ทุกอย่าง · โอนความเป็นเจ้าของได้ (สองฝ่ายยืนยัน) · **ไม่มีทางทำให้ใครเป็น owner ได้จากการแก้บทบาท** |
| `admin` | 46 | ผู้จัดการร้าน | ทุกอย่างยกเว้น `platform.admin.*` |
| `member` | 26 | พนักงานขาย | ลูกค้า ดีล ใบเสนอราคา ประกัน โน้ต รายการติดตาม + `product.read` `chat_session.view/reply` `view_reports` `reassign_records` — **ไม่มี** ใบงาน อนุมัติ รายงานบริการ ทีม บทบาท สมาชิก ตั้งค่า audit |
| `cs` | 19 | ฝ่ายบริการลูกค้า / dispatcher | `ticket.*` `service_report.*` `approval.*` `chat_session.*` + `customer.read/update` `product.read` `audit_log.view` `reassign_records` |
| `technician` | 9 | ช่าง | `ticket.read/create/update/assign/close` `service_report.read/create/update` `product.read` — **ไม่มี** ลูกค้า ดีล อนุมัติ แชทลูกค้า |

> การมอบหมายงาน (`ticket.assign`) อยู่ที่ CS ไม่ใช่ member — เป็นการเลือก least privilege โดยตั้งใจ ร้านที่อยากให้เซลส์มอบหมายได้ต้องสร้างบทบาทเองแล้วติ๊กเพิ่ม

### แคตตาล็อกสิทธิ์ แบ่งเป็นหมวด

| หมวด | key | ความหมาย | บทบาทเริ่มต้นที่มี |
|---|---|---|---|
| ลูกค้า | `customer.read` `create` `update` `archive` | ดู / เพิ่ม / แก้ / เก็บเข้าคลัง | admin, member (cs มี read+update) |
| ดีล | `deal.read` `create` `update` `archive` `reopen` | ดู / สร้าง / แก้ (รวมเปลี่ยน stage) / เก็บ / เปิดใหม่ | admin, member |
| โน้ต | `note.read` `create` `update` | บันทึกบนลูกค้า/ดีล (ไม่มี `note.delete` — ลบใช้ `note.update`) | admin, member |
| รายการติดตาม | `followup.read` `create` `update` | นัดหมาย / เตือน (ยกเลิกใช้ `update`) | admin, member |
| สินค้า | `product.read` | ดูรายการสินค้า (ใช้เลือกรายการในดีล/ใบเสนอราคา) | admin, member, cs, technician |
| สินค้า | `product.manage` | เพิ่ม/แก้/นำเข้าสินค้า | admin |
| เอกสาร | `quote.read` `create` `update` | ใบเสนอราคา (`update` = ออกเอกสาร เปลี่ยนสถานะ ส่วนลด) | admin, member |
| ประกัน | `warranty.read` `create` `update` | ทะเบียนเครื่อง / ประกัน | admin, member |
| งานซ่อม | `ticket.read` `create` `update` `assign` `close` | ดู / เปิด / แก้-รับ-เช็คอิน / มอบหมาย / ปิด-ยกเลิก | admin, cs, technician |
| รายงานบริการ | `service_report.read` `create` `update` | ใบรายงานบริการ (`create` ครอบคลุมเช็คอิน/เช็คเอาต์) | admin, cs, technician |
| อนุมัติ | `approval.view` `approve` `reject` `manage` | ดูคิว / อนุมัติ / ตีกลับ / ตั้งขั้นตอน | admin, cs |
| แชทลูกค้า | `chat_session.view` `reply` | ดูห้อง / ตอบ | admin, member, cs |
| ร้านและระบบ | `member.manage` `role.manage` `team.manage` `setting.manage` | สมาชิก+รหัสเชิญ / บทบาท / ทีมช่างและกลุ่มเซลส์ / ตั้งค่าและข้อมูลบริษัท | admin |
| รายงานและประวัติ | `view_reports` `audit_log.view` | รายงาน AI / ประวัติการใช้งานของร้าน | `view_reports`: admin, member · `audit_log.view`: admin, cs |
| อื่น | `reassign_records` | โอนลูกค้า/ดีลให้ผู้รับผิดชอบคนอื่น | admin, member, cs |
| PDPA | `pdpa.request.view` `pdpa.request.process` | คำขอ PDPA ของร้าน | admin |
| แพลตฟอร์ม | `platform.admin.access` `platform.admin.break_glass` | คอนโซลแอดมิน / โอนเจ้าของฉุกเฉิน | **ไม่มอบให้ร้านใด ๆ** — ของบัญชี platform admin เท่านั้น |

**กฎในไฟล์:** key จะถูกใส่กลับเข้าแคตตาล็อกได้ก็ต่อเมื่อมี route ที่ตรวจ key นั้นจริง (`chat_session.claim`, `chat_session.transfer`, `assignment_rule.manage`, `billing.*` ถูกถอดออกเพราะไม่มีอะไรบังคับ — บทบาทที่ประกอบจาก key พวกนั้นจึงให้สิทธิ์เป็นศูนย์ ซึ่งอ่านเหมือนหน้าบทบาทพัง)

### เส้นแบ่งชั้นที่สอง: OA_ALLOWED_PERMISSION_KEYS

นอกจากสิทธิ์ของบทบาทแล้ว ยังมีเพดานว่า **OA นั้นเสนอความสามารถนี้หรือไม่** เลย (`application/chann_app/services/chat.py::OA_ALLOWED_PERMISSION_KEYS`)

| OA | key ที่ช่องทางนี้ยอมให้ทำ |
|---|---|
| `customer` | `customer.read` `customer.update` `ticket.create` `ticket.read` `warranty.read` `warranty.create` |
| `technician` | `ticket.read` `ticket.update` `ticket.assign` `ticket.close` `service_report.create` `service_report.read` `service_report.update` `warranty.read` |
| `sales` | ไม่จำกัดเพิ่ม (`None`) — บทบาทเป็นตัวตัดสินอย่างเดียว |

**ทดสอบยังไง:** ให้ช่างที่มีสิทธิ์ครบพยายามทำงานฝั่งขาย (`สร้างดีล`, `รายชื่อลูกค้า`) บน Technician OA — ต้องถูกปฏิเสธหรือเสนอสิ่งที่ทำได้แทน **ไม่ใช่** ทำให้ และคำศัพท์ฝั่งขาย (`ดีล`, `ใบเสนอราคา`) ต้องไม่โผล่ในคำตอบบน Technician/Customer OA

## 5. ฟีเจอร์ทั้งหมด แยกตาม OA

หัวใจของเอกสาร ตารางนี้บอก **พิมพ์อะไร → ต้องเห็นอะไร**

ประโยคในคอลัมน์ "พิมพ์แบบนี้ได้" คือประโยคที่ทดสอบแล้วว่าชั้นกติกาเข้าใจ (ผ่าน `scripts/dev/simulate-phrasings.py` และคลังประโยคใน `tests/unit/chat_corpus.py`) แต่ **ระบบตั้งใจให้รับภาษาพูดที่หลากหลายกว่านี้มาก** — ประโยคเหล่านี้เป็นตัวอย่าง ไม่ใช่รายการปิด

### 5.1 Sales OA — แชท

#### ตั้งร้านให้พร้อม

| ฟีเจอร์ | พิมพ์แบบนี้ได้ | ต้องเห็น |
|---|---|---|
| ข้อมูลร้าน / รหัสร้าน | `ข้อมูลร้าน` · `รหัสร้าน` | ชื่อร้าน, รหัสร้าน 8 ตัว (ให้ลูกค้าใช้ผูก), สถานะ, วันหมดทดลองใช้ |

### หน้าแรกฝ่ายขายเป็น "ภาพรวม" ไม่ใช่ตารางลิงก์

`/liff/sales` ตอนนี้แสดง:

1. **การ์ด pipeline** — มูลค่าดีลที่เปิดอยู่ (พร้อมจำนวน) และมูลค่าที่คาดปิดเดือนนี้ · ถ้าไม่มีดีลเลย การ์ดจะไม่ขึ้น (แถวศูนย์ไม่ได้บอกอะไรเพิ่ม) · โหลดล้มเหลวก็เงียบ ไม่พาเมนูล่มไปด้วย
2. **"ต้องตามต่อ"** — จำนวนดีลที่เลยกำหนดปิดและดีลที่ยังไม่มีวันปิด **เป็นลิงก์** ไปหน้าดีล เพราะคำตอบเดียวที่มีประโยชน์คือไปเปิดดู
3. **"เริ่มงานต่อ"** — ทางลัด 4 อันแรก ดึงจากกลุ่ม `งานขาย` ของแถบเมนูเอง จึงไม่มีทางขัดกันว่ามีอะไรและใครเห็นได้

## 8. ข้อจำกัดและพฤติกรรมที่ตั้งใจให้เป็นแบบนั้น

> **AI ที่มาหาบัค ต้องไม่รายงานข้อพวกนี้เป็นบัค**

### พฤติกรรมที่ตั้งใจ

1. **ลูกค้าไม่ถือ permission key ใด ๆ ในแชท** — สาขา `customer` ของ router ตั้ง `permission_keys = []` โดยตั้งใจ (ลูกค้าไม่มีแถว `license_members`) การถามหา "ทำไมลูกค้าไม่มีสิทธิ์ X" จึงไม่ใช่บัค
   *(บนหน้าจอ LIFF ลูกค้าได้ principal ที่ถือ 6 key จาก `CUSTOMER_PERMISSION_KEYS` — สองเส้นทางนี้ต่างกันโดยตั้งใจ)*
2. **`("read","product")` ผูกกับ `product.manage` ไม่ใช่ `product.read`** ในตาราง `ACTION_PERMISSIONS` ของแชท — เป็นเช่นนั้นในโค้ดปัจจุบัน อย่ารายงานว่าตารางผิด (ส่วน route ของหน้าจอ `GET …/products` ยอมรับ `product.read` **หรือ** `product.manage`)
3. **ลิงก์รูปกราฟมีอายุ 1 ชั่วโมง** (`CHART_LINK_TTL_SECONDS = 3600`) ไม่ใช่ 7 วันเหมือนไฟล์อื่น — เพราะ LINE ดึงรูปเก็บไว้เองตั้งแต่ตอนส่ง สิ่งที่หมดอายุคือลิงก์ที่ถูกส่งต่อ
4. **กราฟ 3 ใน 4 แบบนับเฉพาะดีลที่ปิดสำเร็จ (`won`)** — รายเดือน สินค้าขายดี และรายคน ส่วนกราฟ pipeline นับดีลทั้งหมดแยกตามสถานะ · มูลค่าดีลอ่านจากรายการสินค้าถ้ามี ไม่มีก็ใช้ยอดที่พนักงานระบุ (เหมือนที่การ์ด pipeline ใช้)
5. **`ล่าสุด` หมายถึงสิ่งที่อยู่ในบริบทของบทสนทนา** ไม่ใช่รหัสหรือแถวใหม่สุดในฐานข้อมูล — ถ้าไม่มีบริบท ระบบแสดงรายการล่าสุดให้เลือกแทน
6. **ไม่มี `note.delete`** — การลบโน้ตใช้สิทธิ์ `note.update`
7. **ไม่มี round-robin อัตโนมัติ** — `มอบหมายอัตโนมัติ` ทำตามกติกาที่ตั้งไว้ ไม่ได้วนคิว
8. **ลบสมาชิกออกจากระบบถาวรไม่ได้** — ถอดออกจาก OA (`removed`) และคืนสถานะได้ ประวัติยังอยู่
9. **ลูกค้ายังไม่มี flow เซ็นรับงาน** — ลายเซ็นบน PDF มีเฉพาะช่างและผู้อนุมัติ
10. **เช็คเอาต์ไม่บันทึกพิกัด/รูปแยกจากรายงาน** (พิกัดอยู่บนรูป ไม่ใช่บนใบงาน)
11. **รายการยาวมีเพดานต่อการเรียกและยังไม่มีการแบ่งหน้า** (เช่น สินค้า 200 ต่อครั้ง) · ในแชท รายการแสดง **10 แถว** (`LIST_LIMIT = 10`)
12. **`channel` ของสมาชิกมาจากชื่อบทบาทเท่านั้น** — บทบาทช่างที่ร้านตั้งชื่อเอง (ไม่ใช่คำว่า `technician`) จะถูกจัดเป็นช่องทาง `sales` เรื่องนี้อยู่ในรายการที่จะแก้ต่อไป
13. **ความปลอดภัยเป็นแบบ reduced-security ตามขอบเขตโปรเจกต์** — secret ผ่าน env ไม่มี Secret Manager · **ห้ามเสนอหรือเพิ่มทางลัด auth ใด ๆ**

### 11 คู่ (action, entity) ที่ไม่มี handler ในแชท โดยตั้งใจ

ตอบว่าทำในแชทไม่ได้ **พร้อมบอกชื่อหน้าจอที่ทำได้ และปุ่มไปหน้านั้น** — นี่คือคำตอบที่ถูกต้อง ไม่ใช่บัค

| คู่ | ทำที่ไหนแทน |
|---|---|
| `("archive","deal")` | ดีลปิดด้วย stage won/lost · การเก็บถาวรอยู่บนหน้าดีล |
| `("update","deal")` | ไม่มีการแก้ดีลรวบยอดในแชท — stage วันปิด และรายการสินค้าต่างมีคำสั่งของตัวเอง |
| `("update","quote")` | ใบเสนอราคาเปลี่ยนผ่านรายการสินค้าและส่วนลด ซึ่งมีคำสั่งของตัวเอง |
| `("update","warranty")` | แก้ทะเบียนเครื่องทำบนหน้าประกัน · แชทลงทะเบียนและอ่านได้ |
| `("update","approval")` | ตั้งขั้นตอนอนุมัติใช้ `ตั้งค่าการอนุมัติ` ไม่ใช่ intent ลอย ๆ |
| `("delete","product")` | หน้าสินค้าเป็นเจ้าของการลบ · แชทเพิ่มและแก้ได้ |
| `("read","audit_log")` | หน้า audit บน dashboard — บับเบิลไลน์ไล่ประวัติทีละหน้าไม่ไหว |

### 9.5 สิ่งที่ช่องทางในเครื่องพิสูจน์ไม่ได้ (ต้องพูดตรง ๆ ในรายงาน)

- **ตัว LINE เอง** — scenario เรียก chat engine ตรง จึงพิสูจน์ *คำตอบ* ไม่ใช่ว่า LINE เรนเดอร์มันได้: ไม่มีการตรวจลายเซ็น ไม่มี Flex JSON ไม่มี rich menu ไม่มี reply token ไม่มีรูปที่ส่งถึงจริง (`has_image` แค่บอกว่ามี URL แนบมา)
- **ตัวโมเดลภาษา** — ทุกการเรียกโมเดลตอบด้วย stub ตามที่ scenario เขียน พิสูจน์ว่าระบบทำอะไรกับ intent *ที่กำหนดให้* ไม่ได้พิสูจน์ว่าโมเดลจริงจะแปลงประโยคนั้นเป็น intent นั้น
- **หน้าจอ** — ไม่มีเบราว์เซอร์ ไม่มี React ไม่มีการเรนเดอร์ · step `http` ยิง route ของ Application ซึ่งเป็นที่มาของข้อมูลบนหน้าจอ แต่ปุ่มที่พังมองไม่เห็นจากตรงนี้
- **PDF และบริการภายนอก** — SmartBrowz, GCS และผู้ให้บริการชำระเงิน ไม่ถูกเรียก
- **Redis ในฐานะ Redis** — backend `db` แทน Redis ด้วย dict ในโปรเซส · การหมดอายุจริง การ evict จริง และสองโปรเซสใช้แคชร่วมกัน ไม่ถูกครอบคลุม
- **เวลาและการทำงานพร้อมกัน** — step รันเรียงกันในโปรเซสเดียว · race, งานตามเวลา และอะไรที่ต้องรอเข็มนาฬิกาเดิน อยู่นอกระยะ
- **อะไรก็ตามที่ deploy แล้ว** — ไม่มี scenario ไหนแตะ DEV/Stage/Production และไม่ควรมี

## 11. คำศัพท์และรหัส

### รหัสประจำตัวของแต่ละอย่าง

รูปแบบ `X-YYYY-NNNN` โดย `YYYY` คือปี ค.ศ. ตอนที่ออกเลข และ `NNNN` เติมศูนย์ 4 หลัก **นับแยกต่อร้าน** (ไม่ใช่เลขรวมทั้งระบบ)

| รหัส | คืออะไร | ตัวอย่าง |
|---|---|---|
| `C-YYYY-NNNN` | ลูกค้า (Lead และ Contact ใช้แถวเดียวกัน ต่างกันแค่ `stage`) | `C-2026-0001` |
| `D-YYYY-NNNN` | ดีล | `D-2026-0001` |
| `Q-YYYY-NNNN` | ใบเสนอราคา | `Q-2026-0001` |
| `T-YYYY-NNNN` | ใบงานซ่อม (service ticket) | `T-2026-0001` |
| `SR-YYYY-NNNN` | ใบรายงานบริการ (service report) | `SR-2026-0001` |
| `W-YYYY-NNNN` | ทะเบียนประกัน (warranty) | `W-2026-0001` |

### สถานะและ stage

| สิ่งของ | ค่าในระบบ | คำไทยที่ต้องเห็นในคำตอบ |
|---|---|---|
